## 1. What is being fixed and added

- Since V2 2.16.9 the client resolves a hostname to ip addresses before connecting and hands the ip to `SSLSocketFactory.createSocket`, so the JSSE sends no SNI. An endpoint that selects its certificate by SNI (TLS terminating proxy, ingress) serves its default certificate. V3 inherited this: `SocketDataPort.java:170` passes `host`, which `NatsConnection.resolveHost` (`NatsConnection.java:2432`) has already rewritten to the ip in the four resolving modes.
- `HostnameResolveMode.Unresolved` cannot connect without a proxy: `SocketDataPort.java:88-90` always builds the address with `InetSocketAddress.createUnresolved`, which a plain socket rejects with `UnknownHostException`. Measured in V2 (same code). Only the proxy socket implementations accept an unresolved address.
- No hostname verification. Every other client verifies by default; Java has never checked. V3 is new, so the default flips to on, with `tlsVerifyHostname(false)` as the opt-out.
- A server learned from `connect_urls` as a bare ip has no hostname to present as SNI and nothing to verify against but the ip. nats.go has carried the gossiping server's hostname since 2018 (`tlsName`). With verification on by default this is required, not optional: the existing `ReconnectTests` case at `ReconnectTests.java:525` (two `tls_noip.conf` servers, certificate `server_noip.pem` with `DNS:localhost` and no ip SAN, connected as `tls://localhost`, cluster routes on `127.0.0.1`) reconnects to gossiped ips and would fail name verification without the carry-over.

Not in scope: the V2 `noResolveHostnames` remap (V2 commit 2, second half). V3 has no `noResolveHostnames`; `MIGRATION_GUIDE_OPTIONS.md:144` already folds it into `hostnameResolveMode`.

### C. Hostname verification, on by default, opt-out (V2 `960f6818`, default flipped)

- C1 `OptionsProperties`: `String PROP_TLS_VERIFY_HOSTNAME = PFX + "tlsVerifyHostname";` next to `PROP_TLS_FIRST`, javadoc "whether to verify that the certificate the server presents is issued for the server name; default true".

## 7. Open points for the V3 session

- Whether `OptionsBuilder` should also expose a no-argument `tlsVerifyHostname()` for symmetry with `tlsFirst()`; the plan says no, since the default is on.
- Whether V3 wants `connectingServer` as `volatile` like `currentServer`; the V2 field is plain because `handleInfo` runs on the connect path or the reader after the field is set.
- The `tls://demo.nats.io` case in `ConnectTests.java:575` now verifies against the real certificate; confirm that test is gated as it is today.
- **Resolved 2026-10-08 (Scott):** `opentls` is removed from V3 entirely (`PLAN_TLS_CONTEXT_POLICY_V3.md` option C); a supplied trust-all context does not imply verification off, the user adds `tlsVerifyHostname(false)`. The `opentls` test cases change per that plan. Original point: `opentls` and verification. A plain `nats://` connection is unaffected: the check is a parameter on the SSL socket and only `upgradeToSecure` sets it. A trust-all context does not bypass it: the JDK wraps a plain `X509TrustManager` and checks the name in the wrapper (measured in V2, `verifyHostnameAppliesUnderTheTrustAllContext`). With the default on, an `opentls://` connection to a self-signed certificate that does not name the host fails until the caller adds `tlsVerifyHostname(false)`. Go's `InsecureSkipVerify` disables both the chain and the name check. Decide: keep the measured behavior and document it in the migration guide, or make `opentls` (the scheme and `OptionsBuilder.opentls()`) imply `tlsVerifyHostname(false)` to match Go. The plan as written keeps the measured behavior. The wider question of whether V3 builds a trust-all context at all is in `PLAN_TLS_CONTEXT_POLICY_V3.md`.
